# 就活版 企業マッチング 再設計 第二弾 — 「相性診断」から「内定まで導くAI」へ

> 対象: `/career/matching`（就活版）
> 前提: 第一弾 [career_matching_redesign.md](./career_matching_redesign.md) の確定設計を壊さない。
> ステータス: レビュー用ドラフト。
> 確定事項: 内定可能性は MVP では「選考準備度」として % 表示し、「合否を保証しない」注記を必須とする（推測ラベル付き）。較正済み「内定可能性」への格上げは長期（内定者データ学習）で行う。

## 0. 第一弾からの引き継ぎ（不変条件）

- 就活軸 `priorities`/`avoidances` を重みに使う。`avoidances` は減点でなく総合の上限キャップ。
- **AIは部分スコア（軸別fit）＋根拠のみ。総合はサーバが計算**（[ai_score_contract.md](../principles/ai_score_contract.md)）。
- 理由は必ずユーザーデータを引用。事実(Verified)/推測(Inferred)を型で分離。
- MVPはWeb検索なし。

第二弾は AI の担当範囲を広げる（内定可能性・活躍可能性・不足能力・ロードマップ）。**だが総合スコアを計算するのは依然サーバ**。この一線を越えない。

## 1. 実データの現状（設計を縛る前提）

| データ | 実装状況 | マッチングでの使い方 |
|---|---|---|
| 基本情報/活動/就活軸/自己分析/ES | 実装済み・localStorage | そのまま利用（第一弾どおり） |
| 面接AI | 実装済み | `CareerInterviewFinalResult.strengths/improvements`（質的） |
| 相談AI | 実装済み | 質的シグナル |
| **SPI/適性検査** | **enum定義のみ・未実装**（[lib/careerAi/types.ts](../../lib/careerAi/types.ts)） | **データが無い前提**。出たら readiness シグナルに後付け |
| **プレゼン** | 実装済みだが**受験版寄り**（[lib/presentation/](../../lib/presentation/)、DB `presentation_results`、level=1-3） | 就活版接続は別途。数値平均は再利用可能 |

**結論: 全シグナルは「あれば使う／無ければ確信度(confidence)を下げる」。欠損=0点ではない。** これを `Signal { value, present, source }` で表現する（§3）。

## 2. 3つのスコアを直交させる（概念モデル）

「向いている」と「入れる」と「活躍できる」は別物。混ぜると説明できなくなる。**3スコアを独立に定義し、使うデータの重みを変える。**

| スコア | 問い | 主に使うデータ | 性質 |
|---|---|---|---|
| **① マッチ度 (Fit)** | この会社を*望むか*・価値観が合うか | 就活軸(priorities/avoidances), 自己分析の価値観 | 相性。第一弾で確定済み |
| **② 内定可能性 (Offer Readiness)** | この会社に*入れるか* | 選考で評価される成果物: ES, 面接, GD, プレゼン, SPI, ガクチカ(活動の定量実績), 資格/英語 | 競争力 vs 企業の選考バー |
| **③ 活躍可能性 (Thrive)** | 入社後*活躍できるか* | 性格/強み/行動特性/モチベ源泉(自己分析), 職務の成功要因, stressFactorsと社風の摩擦 | 適合。内定とは別軸 |

表示例: `マッチ度92% / 内定可能性68% / 活躍可能性74%`。**3つが乖離すること自体が価値**（「向いてるが今は厳しい」「入れるが活躍は微妙」を可視化）。

### ⚠ 「内定可能性%」の責任ある定義（重要）
内定者データが無いMVP段階で出す数字は、**統計的に較正された確率ではない**。較正データ無しに「68%で内定」と断定するのは事実創作に近く、就活サービスとして危険。
→ **MVPでは「選考準備度 (Readiness Index)」を%表示する**。意味は「選考で評価される要素を、推定される企業の選考バーに対しどれだけ満たしているか」。
→ UIで必ず**「現時点の準備度。合否を保証しません」**と明示し、推測ラベルを付す。
→ 真の較正済み「内定可能性」は長期（内定者データ学習）で初めて成立。較正が入った時点でラベルを格上げする。

## 3. アーキテクチャの心臓部 — 決定的スコアリングエンジン

第一弾の「サーバが総合を計算」を一段押し進め、**全スコアを純粋関数 `score = f(signals, weights, companyBar)` で計算**する。これが③④⑤を全て一つの仕組みから導く。

```ts
type SignalSource = 'measured' | 'inferred';   // 事実 or 推測（型で分離）
type Signal = {
  key: string;            // 'es' | 'interview' | 'spi' | 'gd' | 'presentation' | 'gakuchika' | 'english' ...
  value: number;          // 0-100
  present: boolean;       // データがあるか（欠損対応）
  source: SignalSource;   // measured=既存機能の実数値 / inferred=AIが質的データから推定
  rationale: string;      // なぜこの値か（Explainability）
};

// 純粋関数（LLMを呼ばない）
function offerReadiness(signals: Signal[], companyBar: number, w: Weights): ScoreResult;
function thriveScore(signals: Signal[], roleFactors: Weights): ScoreResult;
function fitScore(...): ScoreResult;   // 第一弾
```

### このエンジンが生む3つの帰結
1. **④⑤がLLM不要で実現**: シミュレーションは `offerReadiness(signals with s_i := s_i')` を再計算するだけ。AI呼び出し0回・即時・完全に説明可能。「実現可能なAI設計」の核心。
2. **③(不足能力の優先度)も同じ関数から**: 各シグナルを一定量上げた時の総合スコアの伸び（感度 Δscore）を全シグナルで計算 → 伸びの大きい順 = 改善優先度。これも純粋計算。
3. **confidence が自動で出る**: `present && measured` の割合からスコアの確信度バンドを算出。SPI未実装/プレゼン未接続でも破綻せず「確信度: 中」と正直に出せる。

### 企業の選考バー (companyBar)
内定可能性には「企業の難易度」が要る。
- MVP: AIが企業の選考難易度ティア(S/A/B/C)を**推測**で出す（inferredラベル必須・根拠付き）。サーバがティア→バー閾値に変換。
- 長期: 内定者データで較正した実バーに差し替え。

## 4. AIとサーバの責任分担（⑦への回答）

| 担当 | AI（部分・質的判断） | サーバ（決定的計算） |
|---|---|---|
| マッチ度 | 軸別fit小スコア＋根拠 | 重み付け合算・avoidancesキャップ |
| 内定可能性 | 質的シグナルの推定値＋根拠（例: ES強度65=ガクチカに定量結果が無い）、企業選考ティアの推測 | **総合 readiness の合算**、companyBar適用、%化 |
| 活躍可能性 | 性格×職務成功要因のfit判断＋根拠 | 総合計算 |
| 不足能力 | 各ギャップの内容説明・どの能力か | **優先順位**（感度Δscore × 改善容易性で並べ替え） |
| 改善ロードマップ | 各ギャップの改善アドバイス文 | **順序決定**（依存関係・締切・レバレッジで sequencing） |
| 改善シミュレーション | （関与しない） | **純粋関数の再計算のみ** |

**原則**: 数値の*判断*はAI、数値の*合算・順位・予測*はサーバ。AIが出した部分値が多少ブレても、総合・順位・シミュレーションはサーバ計算なので一貫し、説明可能。measured シグナル（既存機能の実数値）はAIを通さず直接エンジンへ。

## 5. 各機能の設計

### ① 内定可能性スコア
- readiness シグナル群: `es`(ESのappealPoints/具体性), `interview`(面接strengths/improvements), `gd`, `presentation`(level平均), `spi`(あれば), `gakuchika`(活動のquantitativeResult/scale), `english`(語学/資格), `activity`(実績の厚み)。
- 各シグナル measured か inferred かをタグ。companyBar(推測ティア)で割り引く。
- 出力: `内定可能性(準備度)% + confidence + 効いている要素/不足要素`。**合否保証しない注記必須**。

### ② 入社後活躍可能性
- thrive シグナル: 自己分析の `strengthKeywords/valueKeywords/motivationSources/行動特性` × 職務の成功要因（職種テンプレ＋企業のinferred文化）。
- `stressFactors` と企業文化(inferred)の摩擦を**マイナス要因**として明示（活躍を下げる理由を隠さない）。
- 内定可能性と分離することで「入れるけど合わないかも」を誠実に提示。

### ③ 不足能力分析（優先順位付き）
- ギャップ = 企業/職務の要求 − ユーザーの現エビデンス。
- 優先度 = 感度Δ(そのシグナルを上げた時の内定可能性の伸び) × 改善容易性(残期間で動かせるか)。サーバが並べる。
- 各ギャップに「どのPASSAI機能で埋まるか」をタグ（下表）。

| 不足 | 接続するPASSAI機能 |
|---|---|
| SPI | 適性検査対策(career-aptitude) |
| ガクチカ/自己PR | 活動整理 → ES |
| 面接力・論理性 | 面接AI |
| GD | GD対策(career-gd) |
| プレゼン力 | プレゼン |
| 自己理解の浅さ | 自己分析 → 相談AI |
| 志望整合性 | 企業研究 → ES |

### ④ 改善ロードマップ
- 順序決定はサーバ（AIは各ステップのアドバイス文のみ）。並べ方:
  1. 基盤（自己理解が薄ければ自己分析を最初に）
  2. レバレッジ順（感度Δ大）
  3. 締切近接（選考スケジュールが近い要素優先）
  4. 依存（ES→面接の順序など）
- 出力: `Step1 自己分析 → Step2 ES → Step3 面接 → Step4 SPI` のように、各ステップに「この機能へ」リンクと「埋まる不足」「内定可能性の見込み増」を併記 → ⑤へ直結。

### ⑤ 改善効果シミュレーション（目玉機能）
- **LLMを呼ばない。** `offerReadiness(signals with 改善後の値)` を再計算するだけ。
- 例: 「SPI readiness 40→80 にすると 内定可能性 68%→79%、A社が3位→1位」。
- ランキング変動も同じエンジンで全社再計算 → 並べ替え。即時・無料・説明可能。
- UI: スライダー/ボタンで「もしSPIを伸ばしたら」「長期インターンを足したら」を即反映。
- **注記**: シミュレーション値は「準備度の試算」であり合否予測ではない、と明示。

## 6. 企業カードの進化（⑥）

```
株式会社◯◯
┌── スコア3軸（最上段で一目）──────────────┐
│ マッチ度 92%   内定可能性(準備度) 68%   活躍 74% │
│ [確信度: 中 ⓘ 面接/SPIデータ未取得のため]        │  ← 欠損を正直に
├── 内定可能性の内訳（Explainability）──────────┤
│ ✓効いている: ES具体性, ガクチカ定量実績(measured) │
│ △不足: SPI(未実施), 面接(未実施)  [推測ティア:A] │  ← measured/inferred明示
├── あと何が足りないか（優先順位）──────────────┤
│ 1. SPI対策      → +11%見込  [適性検査へ]          │
│ 2. 面接練習     → +7%見込   [面接AIへ]            │
│ 3. ガクチカ深掘  → +4%見込   [活動整理へ]          │
├── 改善ロードマップ ──────────────────────┤
│ Step1 自己分析 → Step2 ES → Step3 面接 → Step4 SPI │
├── もし改善したら（シミュレーション）────────────┤
│ [SPIを伸ばす ▢] [面接練習 ▢] → 内定可能性 68→79%  │  ← その場で再計算
│ ⚠ 準備度の試算。合否を保証するものではありません    │
├── 活躍可能性の内訳 ──────────────────────┤
│ ✓強みが活きる: 論理性, 主体性                      │
│ ⚠摩擦の懸念: WLB重視 vs 多忙な社風(推測)           │
└── 🔗出典 / ▸次にやるべきこと ──────────────┘
```
UI原則: 上段で3スコアを即把握 → 内訳で根拠 → 不足→ロードマップ→シミュレーションと**下に行くほど行動**。欠損と推測は隠さずラベル化。

## 7. ロードマップ（⑧）

### 🟢 MVP（今あるPASSAI CAREERだけで）
- 決定的スコアリングエンジン（純粋関数）を新設。第一弾のfitに加え offer-readiness / thrive を追加。
- readiness/thrive シグナルは**現存データのみ**から構築（ES/面接/活動/自己分析/相談）。SPI・プレゼンは「present:false」で欠損対応、confidenceに反映。
- 内定可能性は**「選考準備度」として%表示＋合否非保証の注記**。companyBarはAI推測ティア(inferred)。
- 不足能力(優先度)・ロードマップ・シミュレーションは全てエンジンの感度計算/再計算で実装（AI追加呼び出し最小）。
- 企業カード進化（§6）。`logAiUsage()` 必須。

### 🟡 中期（企業データ・Web検索）
- 第一弾§5の `CompanyFacts`(Verified/Inferred) を導入 → companyBar と職務成功要因を出典付きで精緻化。
- SPI機能を実装し measured シグナル化。プレゼンを就活文脈に接続。
- これで内定可能性・活躍可能性の inferred 比率が下がり confidence 上昇。

### 🔴 長期（内定者・実績データ学習）
- 内定者プロファイル × 企業の実データで companyBar とシグナル重みを**較正** → 「選考準備度」を真の「内定可能性」へ格上げ。
- ユーザーの実際の応募/通過結果をフィードバックし重み自動チューニング。
- 「あなたに似た内定者はこう動いた」を改善ロードマップに反映。
- Supabase正本化後に集計基盤を構築。

## 8. 設計が守る原則（チェック）
- [ ] AIは部分スコア＋根拠のみ。総合/順位/シミュレーションはサーバ純粋関数（score_contract維持）
- [ ] 3スコアを直交定義し混ぜない
- [ ] 内定可能性は「準備度」と明示し合否を保証しない（事実創作の回避）
- [ ] 全シグナルに measured/inferred タグ（事実/推測分離）
- [ ] シグナル欠損で破綻せず confidence に反映（SPI未実装/プレゼン未接続でも動く）
- [ ] 各不足は必ずPASSAI機能へ接続（ナビゲーション化）
- [ ] シミュレーションはLLM不使用（実装可能性）
- [ ] 全AI呼び出しに `logAiUsage()`
